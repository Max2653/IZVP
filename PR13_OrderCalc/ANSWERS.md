# ПР13 — Розрахунок замовлення (відокремлення UI від бізнес-логіки)

## Структура

- `OrderCore/OrderService.cs` — бізнес-логіка: перевірка даних і розрахунок. Не залежить від Windows Forms.
- `OrderApp/` — GUI (Windows Forms): поля «Сума», «Знижка», кнопка «Розрахувати». Лише передає дані в сервіс і показує результат.
- `OrderConsoleDemo/` — виклик того самого сервісу **без GUI** з автоматичною перевіркою сценаріїв.

Запуск: `dotnet run --project OrderApp` (вікно), `dotnet run --project OrderConsoleDemo` (перевірка без GUI).

## Відповіді на запитання

**1. Яка логіка винесена у сервіс і чому її не слід залишати в обробнику кнопки?**
У `OrderService` винесено: перетворення введеного тексту на число (з комою або крапкою), перевірку правил (сума ≥ 0, знижка 0–100%), обчислення суми знижки з округленням і підсумку до сплати. Якщо тримати це в обробнику кнопки, логіку неможливо перевірити без запуску вікна, її не можна повторно використати (наприклад, у вебверсії чи консолі), а будь-яка зміна інтерфейсу ризикує зламати розрахунок. Окремий сервіс простіше тестувати й супроводжувати: GUI відповідає лише за показ, сервіс — за правила.

**2. Як дані передаються з GUI до сервісу та результат повертається у вікно?**
Обробник кнопки бере `Text` полів «Сума» і «Знижка» та викликає `_service.Calculate(amountText, discountText)`. Сервіс повертає об'єкт `OrderResult` (`Success`, `Total`, `DiscountValue`, `Error`). Форма перевіряє `Success`: якщо `true` — показує «До сплати: … грн» зеленим, якщо `false` — показує текст `Error` червоним і в `MessageBox`. Сервіс передається у форму через конструктор (`new MainForm(new OrderService())`), тож форма не створює логіку сама.
